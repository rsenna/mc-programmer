# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Purpose

Three parallel libraries — Python (`python_lib/mc_programmer/`), Swift
(`swift_lib/Sources/MCProgrammer/`), and Rust (`rust_lib/src/`) — for
programming the Roland MC-101, MC-707 and MV-1 grooveboxes via MIDI System
Exclusive. All three share the same data model, parameter table, and test coverage.

The original experimental Python scripts that this project derived from
(see git history for `hack_tools.py`, `seq_tools.py`, `sys_ex_comm.py`,
etc.) have been removed from the repo root. The two video transcripts
they came with are still in [`reference/`](reference/) — they document
the sequencer encoding and ZEN-Core layout that the libraries
implement.

## Running

### Python

```bash
PYTHONPATH=python_lib python -m unittest discover -s python_lib/tests
```

76 tests, including six generator regressions. The library has zero hard dependencies; install
`python-rtmidi` (or use `pip install -e python_lib[rtmidi]`) to get the
real-hardware transport.

### Swift

```bash
cd swift_lib
swift test
swift run MCProgrammerExamples
```

44 tests, ~8 seconds in a local run. The full dump/restore path remains
covered; file serialization uses a compact fixture. Linux builds remain
supported because CoreMIDI-only code is conditionally compiled.

### Rust

```bash
cd rust_lib
cargo test --all-features
cargo run --example four_on_the_floor
```

188 tests with all features enabled; the crate declares Rust 1.71 as its MSRV.
The default crate has no MIDI backend; enable the optional `midir` feature
for CoreMIDI on macOS, ALSA on Linux, or WinMM on Windows.

## Architecture

The three libraries are layered. From top to bottom:

1. **High-level helpers** (`MCClient.place_note`, `set_pattern`,
   `clear_clip`, `select_scene`, `select_clip`, `dump_tone`,
   `Project.dump_from`, …) — front-panel-numbered (1-based), accept
   note names *or* MIDI numbers. The musician-facing API.
2. **Generic primitives** (`MCClient.read_zc_param`,
   `write_zc_param`, `read_note_step`, `write_note_step`,
   `read_chunked`, `write_chunked`) — 0-based `_idx` parameters,
   developer-facing.
3. **Sequencer codec** (`NoteStep` / `NoteComponent` /
   `encode_note_step` / `decode_note_step`) — encodes/decodes the
   256-byte note step record per the MC programming video.
4. **ZEN-Core parameter framework** (`ZCParam`, `lookup_param`,
   `substructure_offset`) — knows the address layout of every
   substructure inside a tone descriptor; the actual ~389-entry
   parameter table is auto-generated by `tools/gen_zencore_params.py`
   from the Jupiter-X PDF.
5. **Address map** (`AddressMap.note_step_address`,
   `zencore_tone_address`, `clip_base`, …) — pure address arithmetic.
6. **Sys-Ex protocol** (`build_rq1`, `build_dt1`, `parse_dt1_payload`,
   `roland_checksum`) — message framing.
7. **Transport** (pluggable) — `LoopbackTransport` (in-memory fake MC),
   `RtMidiTransport` / `MidoTransport` (Python), `CoreMIDITransport` (Swift),
   `MidirTransport` (Rust), and `NullTransport` (test stub).

### Key invariants

- **No address byte may have its MSB set** — the
  `0x80808080` mask in the reference scripts. `AddressMap` automatically
  skips clip-base candidates that violate this.
- **Empty note slot** in a 256-byte step record is encoded as the
  nibble pair `0x0F 0x0F` (decoded as `0xFF` = `EMPTY_NOTE`).
- **Tied note** has `end_cents == 100` in the previous step.
- **Roland octave convention**: middle C is **C3 = MIDI 60**, kick
  drum is **C1 = 36**.
- **Indexing**: low-level `*_idx` parameters are 0-based. High-level
  `track`/`clip`/`step` parameters are 1-based and match the MC's
  front-panel labels.
- **MC-101 has 4 tracks**, MC-707/MV-1 have 8. `MCClient.num_tracks`
  reflects this; high-level helpers and `Project.dump_from()` respect
  it automatically.

### Parameter framework

The MC family uses **both halves of the ZCore tone descriptor** —
conventional `[Tone Common]` / `[Tone PMT]` / `[Tone Partial]` *and*
the `[Tone Synth Common]` / `[Tone Synth PMT]` / `[Tone Synth Partial]`
sub-block. All 12 substructures are wired in:

| Group | Address | Where defined |
|---|---|---|
| `common` | `0x0000` | `[Tone Common]` |
| `mfx` | `0x0100` | `[MFX]` (272 bytes) |
| `pmt` | `0x1000` | `[Tone PMT]` |
| `partial` ×4 | `0x2000+` step `0x100` | `[Tone Partial]` |
| `partial_pitch_env` ×4 | `0x2400+` step `0x100` | `[Partial Pitch Env]` |
| `partial_filter_env` ×4 | `0x2800+` step `0x100` | `[Partial Filter Env]` |
| `partial_amp_env` ×4 | `0x2C00+` step `0x100` | `[Partial Amp Env]` |
| `partial_lfo` ×4 | `0x3000+` step **`0x200`** | `[Partial LFO]` |
| `partial_eq` ×4 | `0x3800+` step `0x100` | `[Partial EQ]` |
| `synth_common` | `0x3C00` | `[Tone Synth Common]` |
| `synth_pmt` | `0x3D00` | `[Tone Synth PMT]` |
| `synth_partial` ×4 | `0x3E00+` step `0x100` | `[Tone Synth Partial]` |

The Partial LFO has the larger `0x200` stride because the struct is
0x11E bytes (it carries both LFO 1 and LFO 2 in one block).

## Regenerating the parameter table

The `python_lib/mc_programmer/zencore_data.py` and
`swift_lib/Sources/MCProgrammer/ZenCoreData.swift` files are auto-generated
and committed, so the libraries work without ever running the
generator. To rebuild from a fresh Jupiter-X PDF, follow the
step-by-step in [`reference/README.md`](reference/README.md) — it
walks through downloading the Roland PDF locally and running the
extraction commands.

To **add** a new substructure to the table, first append its
`pdftotext -raw` extraction to your locally-downloaded
`reference/tools_jp_zcore.txt` (in the same `* [Section Name]` format
the existing entries use), then add an entry to `SECTION_NAME_MAP` in
`tools/gen_zencore_params.py` mapping the raw header to a Python
variable name. Re-run the generator. **Do not commit
`reference/tools_jp_zcore.txt`** — the `.gitignore` will block it
anyway.

## Notes for Claude Code

- **The libraries' parameter table is sourced from the Jupiter-X PDF**
  because that's the only Roland document publishing byte-level
  Sys-Ex addresses. The MC-707 / MC-101 reference manuals document
  the parameter *names* and *ranges* but not the addresses. The
  Jupiter-X engine is the same ZEN-Core engine, so the inner layouts
  match. Per the ZC programming video, this is explicitly stated by
  Roland's engineers.
- **Don't fabricate addresses you can't verify.** If a parameter isn't
  in the existing reference scripts (now in git history) and isn't in
  the Jupiter-X PDF, mark it as pending in [ROADMAP.md](ROADMAP.md)
  rather than guessing. There are real risks of corrupting user
  patches.
- **Indexing convention is enforced by parameter name**: `_idx` →
  0-based array index, no `_idx` → 1-based front-panel number. Don't
  mix the conventions in the same method.
- The sequencer encoding (256-byte step record, 16 lanes, end-time tie
  at 100) comes from the MC programming video and is verified against
  the reference scripts. See [`reference/MC_Programming_Video.txt`](reference/MC_Programming_Video.txt).
